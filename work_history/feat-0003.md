## The design constraint that shaped the ticket

`charts/soundings/templates/api-deployment.yaml` wires `startupProbe`,
`readinessProbe` **and** `livenessProbe` all to `/healthz`. This ticket adds
a Garage `head_bucket` call to that endpoint. With boto3's ~60s default
timeouts and multiple retries, a Garage outage would hang the liveness probe
and crashloop every api pod in **both** slots — a total outage caused by a
dependency not yet on the critical path.

Three mitigations, all tested:
1. A separate health client bounded at 2s connect / 2s read / 1 retry, built
   once at construction rather than per request.
2. `healthcheck()` catches broadly and returns `"error"` in the body; it
   never raises. The broad `except` is deliberate and commented as such so
   nobody "cleans it up".
3. Tests assert HTTP 200 explicitly in every case, including one that fires
   an *unstubbed* botocore call inside `healthcheck()` to prove nothing can
   escape. That assertion is the regression guard.

Env names were read off the live chart rather than guessed (`S3_ENDPOINT`,
`S3_REGION`, `S3_BUCKET`, `S3_FORCE_PATH_STYLE` from `config:`;
`S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` from the `soundings-app`
Secret). A mismatch would have made a fully-configured cluster report
`unconfigured` — green everywhere except the one check that matters.

## Notes for the tickets that copy this

- `S3MediaStore` takes configuration as constructor arguments and never
  reads the global `settings`; `deps.py` is the single place the global is
  touched. That is what makes it constructible against a botocore `Stubber`,
  and SB2/RC1 should keep it.
- boto3 ships no type stubs. Under pyright strict the `Unknown` taint from a
  direct `boto3.client(...)` survives an explicit `: Any` annotation and
  resurfaces at each later use; it is absorbed at exactly one boundary in
  `_build_client`. No `type: ignore`, no stub dependency, no weakening of
  the global pyright config.
- No test touches the network or a container. This laptop cannot reach
  Garage by design and nothing here tries to.

## Friction (dogfooding)

- **Process slip:** the implementation was dispatched before the branch was
  claimed, so the subagent edited on `main`. No work was at risk
  (uncommitted changes follow a `checkout -b`) and the claim mark was
  committed to `main` while the subagent ran, but the correct order is
  claim → dispatch. `branch-new` also never wrote its stub, so
  `.tickets/feat-0003.md` was written by hand afterwards.
- The Bash tool's cwd drifted out of the repo again after a `cd` into
  another tree, and a `tea pulls merge` + `git` compound command half-failed
  because of it. Third occurrence across two tickets — use absolute paths in
  every compound command. (Same note in `docs-0006`.)
- `tea pulls merge` rejects `--delete-branch`; the remote branch needs a
  separate `git push gitea --delete`.
