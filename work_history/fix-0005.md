## The actual defect

A `-> StreamingResponse` return annotation carries no media-type
information, so FastAPI fell back to documenting the 200 as
`application/json` with an empty schema. The route had been streaming
correct binary the whole time — SB2's deployed check round-tripped 1 MB
through Garage with a correct `Content-Type` and `ETag`. Only the
*contract* was wrong, and it propagated: `schema.d.ts` typed the response
as JSON `unknown`, which is why SB3a declined to write a download call
site and filed this instead.

Contract diff, entire:

```diff
-              "application/json": { "schema": {} }
+              "application/octet-stream": {}
```

## How "no runtime change" was actually checked

Not by inspection. The route already carries runtime coverage —
`tests/test_idea_assets.py:145` round-trips the download, `:198` asserts
the 404 after delete — and both still pass. `response_class` is inert for
this handler because it returns a `StreamingResponse` directly; it is
there so FastAPI documents the media type.

## Deliberately not done

The generated `data` is `unknown`, not `Blob`, because the media-type
object is empty (`"application/octet-stream": {}`, no schema).
`parseAs: 'blob'` is what makes the call site type correctly, and
`typecheck` proves it. Giving the response a
`{"type": "string", "format": "binary"}` schema would produce a more
specific generated type, but FX1's acceptance criteria asked only that the
200 name a binary content type. Left as a possible refinement rather than
quietly widened — if SB3b finds `unknown` awkward, that is the ticket to
raise it in.

`downloadIdeaAsset` has no direct test: it is unused until SB3b's
attachments panel consumes it, which is the ticket that asked for it.
