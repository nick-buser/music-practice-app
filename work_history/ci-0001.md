## The find (pipelines #11/#12, red)

The first CI run failed on exactly the step that had no local proof:
`test_jsonb_and_defaults_roundtrip_on_postgres` hit a
`ForeignKeyViolation` — `saved_chords.user_id` referencing a `users` row
that wasn't there yet — while every other step, including the Alembic
round trip, passed.

**Cause:** there is no `relationship()` anywhere in `app/models/`. The FK
is a bare column constraint on `OwnedMixin`. SQLAlchemy's unit of work
orders cross-mapper inserts within a flush from ORM *relationship*
dependencies, **not** from column-level foreign keys, so a `User` and a
`SavedChord` added to one Session and committed together have no
guaranteed insert order. SQLite has `PRAGMA foreign_keys` OFF by default
and never enforced the constraint; Postgres does.

The bug was **pre-existing**, inherited verbatim from the testcontainers
version of the test, which had never actually executed — its Docker probe
always skipped on this laptop. Fix was test-side only (`s.flush()` before
adding the chord). The application is unaffected: `app/seed.py`'s
`ensure_default_user()` commits the user in its own transaction.

**Carry forward — this is the reusable part.** SB1 (`ideas`/`idea_links`),
PV1 (provenance keyed by subject) and RC1 (`recordings`/`recording_tracks`)
all add FK-carrying child tables. Any test of theirs that creates a parent
and a child in a single `commit()` will pass on SQLite and fail on
Postgres in exactly this way. Either add real `relationship()`s or flush
parents first — and note that only the `integration` suite can catch it.

## Friction (dogfooding)

- `branch-new` hardcodes `git fetch origin` / `git pull --ff-only origin`,
  but this repo's forge remote is `gitea`; `origin` is the GitHub showcase
  mirror and is deliberately many commits behind. It worked only because
  `origin/main` is an ancestor of local `main`, so the pull was a no-op.
  It will misbehave the moment the mirror diverges. (Same note was filed in
  docs-0006 — second occurrence.)
- `tea pulls merge` rejects `--delete-branch`; the branch has to be deleted
  separately with `git push gitea --delete <branch>`.
- The ticket's own scope did not mention `uv.lock`. Removing a dependency
  without re-locking would have failed CI at `uv sync --frozen` — the
  *first* step, before anything the ticket added ever ran. Grooming for
  dependency-touching tickets should name the lockfile explicitly.
