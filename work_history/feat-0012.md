## The three failure modes this code invites, and how each is handled

1. **Feature detection as a crash.** jsdom, an insecure context, and older
   browsers all legitimately lack `MediaRecorder`/`getUserMedia`. Detected
   once on mount — never at module scope, never during render — exposed as
   a `supported` boolean, and the control simply does not render without
   it.
2. **A hardcoded mime.** `audio/webm;codecs=opus` only when
   `MediaRecorder.isTypeSupported` agrees; otherwise the option is omitted
   and the browser default applies, and the Blob always carries
   `recorder.mimeType`. Claiming a codec the recorder did not produce would
   poison the stored asset's metadata for every later extractor.
3. **A microphone that never switches off.** Every stream track is stopped
   on the abort path, in `onstop`, and in the unmount cleanup, with a
   dedicated "releases every stream track on unmount mid-recording" test.

Permission denial lands in `recorder.error` and returns `state` to `idle`
rather than throwing. The upload is two calls, and a failed track upload
surfaces in the UI rather than letting the user believe the take was saved.

## Criterion 4 is NOT met — deliberately

> "record ten seconds on the dev slot in desktop Chrome, reload, the take
> plays back (substrate: deployed, hardware)"

`loop.md`'s Substrates table defines `hardware` as "never an admission
input: lines tagged `hardware` are verify notes, not gates". It needs a real
microphone and a person at the keyboard. The loop cannot close it, so it is
left visibly open in `.tickets/feat-0012.md` rather than ticked. This is the
first ticket in the run with an acceptance criterion the loop is structurally
unable to satisfy, and recording it honestly is the whole point of the
`hardware` tag existing.

## Known trade, flagged rather than buried

`GET /v1/recordings` returns `RecordingSummary` **without** tracks by design
(RC1's own doc comment says so), so `useRecordings` follows up with one
`getRecording` per summary to obtain a track id for `<audio src>` — an N+1.
Fine for a subject-scoped list; worth revisiting if a global list ever needs
it. Recorded in the PR body too, so a reviewer meets it before the code.

MIDI-in-parallel tracks stay deferred to the SB7 follow-up as the ticket
specifies. `uploadRecordingTrack` accepts `kind: 'midi'` for that work;
nothing calls it yet.
