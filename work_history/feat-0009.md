## Why this one was worth T2

Every later extractor ticket (PV3, PV5, RC5) copies this shape, so the
decisions here are the ones that get repeated:

- **The claim is its own short transaction**, deliberately not folded into
  the execute-and-finish one, so a run visibly shows `running` to a
  `GET /runs/{id}` poller for the whole duration of extraction.
- **The success path commits properties and the `succeeded` flip
  together.** Any exception rolls that back *before* `failed` + `error` are
  written separately — which is what makes "no partial properties survive a
  failure" true rather than hopeful.
- **No broker, no retry policy, on purpose.** A `failed` run sits with its
  error text for a human or a later ticket.

## Two places the work refused to overclaim

Worth recording because both are the failure mode this loop's admission
rules exist to prevent — a green test that cannot fail for the reason the
ticket exists.

1. **The dialect split.** `_claim_oldest_queued` uses
   `FOR UPDATE SKIP LOCKED` on Postgres and a plain select on SQLite. The
   suite runs on SQLite, so criterion 2's test proves *sequential*
   double-claim only. The docstring says so outright: the concurrency
   guarantee comes from the SQL semantics of `SKIP LOCKED`, not from that
   test. Per `loop.md` the Postgres path is `ci` (OPS2) / deploy-verified.
2. **Criterion 3 would have passed trivially.** The shared `client` fixture
   never enters `TestClient` as a context manager, so FastAPI's lifespan
   never fires — asserting "no worker thread started" against it proves
   nothing at all. The test drives lifespan explicitly instead.

## Deployed criterion — MET

Enqueued a real `sha256-echo` run against `soundings-dev` after the merge
rolled:

- created `queued`, reached **`succeeded` at t+3s** (`startedAt`
  02:33:24.881 → `finishedAt` .892 — 11 ms of actual execution)
- the worker wrote the property: `kind: sha256_echo`,
  `payload: {"inputSha256s": ["aa","zz"]}`, tied to that run
- `paramsHash` computed over the nonce with `inputSha256s` folded in — PV1's
  run-identity machinery working underneath

The check posts a **nonce in `params`** deliberately: run identity is unique
on `(subject_kind, subject_id, extractor, extractor_version, params_hash)`,
so a fixed body would be a cache hit returning the *previous* run, and the
check would pass against nothing.

## Friction log

- **My wrapper script's final line lied.** The strict check printed
  `PASS run reached 'succeeded' within 30s`, then the *bonus* property
  verification crashed, and the wrapper's catch-all summary printed
  `FAIL the enqueued run never reached 'succeeded' on the dev slot`. The
  criterion had passed; the summary said the opposite. A failure line that
  restates a hypothesis instead of the observed result is worse than no
  summary — if a wrapper reports, it must report what actually happened at
