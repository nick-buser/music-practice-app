## The two design calls, and which one the machine settled

**1. `search_tsv` is not a mapped ORM column.** The groomed scope said
"model declares the column with a SQLite no-op variant". That does not
survive contact with SQLAlchemy 2.0: there is no per-dialect `Computed()`,
so mapping it forces `Base.metadata.create_all()` — the SQLite test path —
to emit either a `GENERATED ALWAYS AS` expression SQLite cannot execute, or
a plain, never-populated `tsvector` on Postgres that silently diverges from
what the migration builds. `IDEA_SEARCH_TSV = column("search_tsv",
TSVECTOR)` is a bare expression instead: a name plus a type to build SQL
against, with no mapper and no `create_all()` involvement. Only the
Postgres branch references it.

Consequence worth remembering: **the integration test has to run the real
migrations, not `create_all()`**, because the column does not otherwise
exist. That is a stronger test than the module's older ones, which build
their schema from `Base.metadata`.

**2. The generation expression has to be IMMUTABLE, and only CI could say
so.** A `STORED` generated column requires it. The two-arg
`to_tsvector('english', …)` is immutable; the one-arg form reads
`default_text_search_config` and is merely `STABLE`, which Postgres
rejects outright. `tags::text` on a `jsonb` column is immutable. None of
this is checkable on this laptop — no Postgres, no container runtime by
design — so it went in as a reasoned bet with the `ci` criterion as its
gate. Pipeline #64's log settled it: `Running upgrade 0006 -> 0007,
ideas_search` succeeded. The bet was right, but it was CI that made it a
fact rather than a claim.

## What CI caught that eight green local gates could not

Pipeline #64's `test-postgres` step failed:

```
IntegrityError: (psycopg.errors.UniqueViolation)
  duplicate key value violates unique constraint "users_pkey"
  DETAIL: Key (id)=(00000000-0000-0000-0000-000000000001) already exists
```

The new test copied `s.add(User(id=DEFAULT_USER_ID, …))` from its three
neighbours in `test_integration_postgres.py`. Those neighbours are right —
they build their schema with `create_all()`, which seeds nothing. This test
runs the migrations, and `0001_initial` **inserts the default user itself**,
so the copied line duplicated it. Fixed with `app.seed.ensure_default_user`,
which is idempotent and therefore correct on both paths.

The generalisable bit: *within one test module, two tests can have
incompatible setup requirements because they build their schema by
different routes.* Copying the local idiom was the reasonable move and it
was still wrong. Nothing on this laptop could have caught it — the test is
`-m integration`, deselected here, and the default suite stayed 128-green
through the whole failure.

This is the `ci` substrate earning its place in `.tickets/loop.md`. Two
separate facts about migration 0007 — that its expression is immutable, and
that its test's fixture was broken — were both invisible locally and both
surfaced in one CI run.

The `zzznomatch` row is the one that matters: `?q=hello` returning one row
would have looked identical if `q` were being ignored *and* there happened
to be one idea. Two queries make it a check instead of a coincidence.

## Smaller decisions, recorded

- **Explicit `?status=` and a `q=status:` AND rather than union** when both
  are given. The criterion only required they agree when used alone;
  independent predicates are the less surprising reading of "filters".
- **The frontend skips its defensive recency resort while a search is
  active.** `useIdeas` has always re-sorted by `capturedAt` rather than
  trust wire order. Left alone, that would silently discard Postgres's
  `ts_rank` ranking on every search — shipping ranked search and then
  un-ranking it in the client. Ordering is now trusted only when `q` is set.
- **Out-of-order responses guarded with a request-id ref**, not an
  `AbortController`. A debounced box fires overlapping requests; a slow
  response for an earlier query must not overwrite a faster later one.

## Friction log

- `~/.claude/skills/woodpecker/bin/wp` hardcodes `ci.lab`, which does not
  resolve off-LAN; every call in this session went through
  `https://ci.bittern-chameleon.dev` by curl instead. `WP_BASE` did not
  override it. Worth a fix in that skill.
- Free text on the SQLite branch interpolates into `LIKE '%…%'` without
  escaping `%` or `_`, so searching for a literal `%` behaves as a wildcard.
  Harmless at this app's scale and on the Postgres path, but it is a real
  edge and is recorded here rather than fixed out of scope.
