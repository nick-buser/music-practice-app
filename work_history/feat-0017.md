## Why this one was T2

Two later tickets build directly on these modules — SR6 (sight-reading
assessment) and SC9 (structured score entry) — so the option shapes chosen
here are their constraints, not this ticket's private business. That is what
"first-of-kind pattern-setter" means in the tier ladder, and it is why the
F2 amendment had already specified `MidiRecorder`'s constructor options
before a line was written.

Those options are honoured literally:

- `origin: 'first-note'` anchors the clock at the first note-on (the
  sketchbook's case). `origin: 'external'` takes SR6's count-in downbeat as
  `t0Ms` and must **not** re-anchor.
- `silenceTimeoutMs: null` disables the timeout outright rather than
  falling back to a default. A recorder that read `null` as "use 10 s"
  would silently truncate a sight-reading attempt mid-phrase — which is
  precisely the fork the amendment exists to prevent. Tested directly.

## The check the encoder's own tests could not make

A hand-rolled binary encoder is the canonical case where an author's tests
prove nothing: expected bytes obtained by running the encoder merely assert
it reproduces itself. Two independent things happened here.

The implementer derived `smf.test.ts`'s expected bytes from the SMF 1.0
spec and cross-checked them against a from-scratch Python implementation
before writing them into the test.

**Separately, in the orchestrating session**, the real `encodeSmf` was
driven with a fixed three-note sequence and the output parsed by the
backend's own `mido` extractor — `app/jobs/extractors/midi_features.py::
_parse`, the actual consumer this encoder has to satisfy. Exact round trip:

```
type 0, ppq 480, 1 track
set_tempo 625000 µs/quarter        ← 60000000/96, from tempoBpm: 96
text meta at tick 0, marker 'bar1' at tick 480, end_of_track present
_parse → 60 @ 0.0–0.5s, 64 @ 0.5–0.75s, 67 @ 1.0–2.5s
         (input: 0/500ms, 500/250ms, 1000/1500ms)
```

Worth recording as a loop habit: for a ticket whose output is *bytes another
component reads*, the orchestrator's verification step should drive the real
encoder into the real consumer. That is a different claim from "the tests
pass", and it is cheap — one scratch test file and one `mido` call.

## Design decisions, recorded because SR6/SC9 inherit them

- **Note-on with velocity 0 is a note-off.** The universal keyboard
  convention, and the thing that bites anyone handling only `0x80`.
- **Unmatched note-off:** dropped — there is no onset to build a note from.
- **Note still held at `stop()`:** closed at that instant rather than
  discarded, the same judgment `midi_features._parse` already makes for a
  truncated file. Consistency with the backend parser matters more here than
  either choice does on its own.
- **Running status: not emitted.** Every event carries a full status byte.
  Simpler, sidesteps the "meta event resets running status" failure mode,
  and costs nothing at this file size.
- **`unsupported` and `denied` are different states.** `useMidiInputs`
  exposes four, so the button is hidden entirely on Safari, jsdom and the
  public static build, but shown with a retryable error to someone who
  declined the prompt. Collapsing those two would tell a user who can be
  helped that the feature does not exist.
- **Channel 0 for everything.** Neither the recorder's note list nor either
  caller carries a per-note channel; multi-channel is out of scope and
  marked as such rather than half-supported.

## Friction log

- **TS 5.9's `Uint8Array<ArrayBufferLike>` vs. `File`'s `BlobPart`**
  (`ArrayBufferView<ArrayBuffer>`) fails typecheck on `new File([bytes], …)`
  for reasons having nothing to do with encoder logic. Fixed by pinning
  `encodeSmf`'s return type to `Uint8Array<ArrayBuffer>`. **SR6 and SC9 will
  hit this the moment they hand `encodeSmf`'s result to a `File`/`Blob`** —
  recorded here so they don't rediscover it.
