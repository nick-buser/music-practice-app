## One deliberate addition beyond the ticket

`CheckConstraint("(subject_kind IS NULL) = (subject_id IS NULL)")`. The
scope note said the pair "move together"; this makes that a database
guarantee instead of a routes-only convention, so a half-set subject cannot
be written by any path. Kept, and called out in the PR rather than slipped
in.

## What could NOT be verified locally — and the ticket it produced

`uv run alembic upgrade head` **fails on the first revision** under SQLite:

```
CompileError: (in table 'saved_chords', column 'identity'):
  can't render element of type JSONB
```

`migrations/versions/0001_initial.py:45` declares the column as a bare
`postgresql.JSONB()` where every later revision uses
`JSON().with_variant(JSONB(), "postgresql")`. Reproduced independently
against a clean SQLite file, and confirmed `0001` is untouched by this
branch — it is pre-existing.

The consequence is larger than this ticket: **no migration in this repo has
ever been verifiable on this laptop**, because there is no Postgres and no
Docker by policy. Every schema ticket has had to substitute something
weaker. Here that substitute was driving `0005`'s own
`upgrade → downgrade → upgrade` through alembic's `Operations` API against a
real SQLite file (both tables appear, disappear, reappear; both
`CheckConstraint`s fire), plus adding `recordings`/`recording_tracks` to
`tests/test_integration_postgres.py`'s `APP_TABLES` so the authoritative
round-trip runs in CI — which it then did, green, on #49/#50.

Filed as **FX4**. It is one line of cause for a permanent tax.
