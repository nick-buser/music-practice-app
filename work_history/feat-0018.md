## The expectation this ticket beat

At claim time this was recorded in the ticket as unlikely to close in one
dispatch, with instructions to land only what genuinely passed and re-groom
the rest. It closed all nine. Worth noting *why* the pessimism was
reasonable and wrong: the spec was unusually complete (1,157 lines, plus 22
committed empirical probes), so the ticket was large but not underspecified.
**Size and ambiguity are different risks, and only the second one actually
defeats a single dispatch.** A better claim-time question than "how big is
this" is "how much of this has to be discovered rather than read".

## Verovio does not behave the way its docs suggest

That is the entire reason this ticket exists, and `docs/probes/` is the
repo's record of it. Two failures found here by measuring, not reasoning:

1. **An early `groupBeams` never closed its `<beam>` elements.** Verovio
   still returned `loadData → 1`, with an **empty log**, and rendered a
   plausible-looking score with entire staves and measures silently missing.
   That is `exp19` reproduced live, and it is exactly why `validateScoreDoc`
   — not the renderer — is the gate. A renderer that never reports failure
   cannot be one.
2. **`renderToSVG` called twice on one load produces different bytes.** The
   glyph `<symbol>` suffixes come from the id RNG, which advances per
   *render*, not per load. Byte-identity is a property of
   re-seed → `loadData` → render, which is what `renderScoreDoc` does. A
   determinism test written the obvious way — two renders, one load — would
   have passed locally and flaked in CI.

## Independent verification, and why it was worth doing

Gate results are always re-run in the orchestrating session. But for
criteria phrased as "byte-identical" and "equals Verovio's own answer", a
green suite written by the same agent that wrote the code is weak evidence:
the failure mode is a test that asserts a function reproduces its own
output. So a separate audit was written against the modules, deliberately
not reusing the ticket's test helpers:

| Fixture | SVG identical across 2 independent toolkits | Note ids exactly once as `<g id>` | StaffDef ids in SVG | Pitch mismatches |
|---|---|---|---|---|
| grandStaffExercise | yes (112,030 bytes) | 51 / 51 | none | 0 |
| gMajorSpelling | yes (73,787) | 8 / 8 | none | 0 |
| fMajorSpelling | yes (74,069) | 8 / 8 | none | 0 |
| windowed | yes (104,222) | 48 / 48 | none | 0 |

Sounding pitch was checked by calling Verovio's own
`getMIDIValuesForElement(id).pitch` and comparing against `midiOf`, for
every note including the double accidentals and the cautionary.

The implementation's own tests were also read rather than trusted. They hold
up: determinism is compared across separately-constructed toolkits (not two
calls on one), there is a deliberate option-poisoning case per `exp21`, and
validity has 20 named negative fixtures each pinned to a specific
`IssueCode`.

## A criterion that is literally false and substantively true

Criterion 3 says "no `sd…` id appears at all". Taken literally that is false:
Verovio independently mints ids beginning with `sd` (`sdhioz2`, `sdco0s4` in
these renders). Each was checked against the document's own id set — **none
is a ScoreDoc id**, and the fixture's real StaffDef ids (`sdso06a7szxr`,
`sdyyfaualnqm`) appear nowhere in any SVG. The intent holds; the phrasing
collides with Verovio's id alphabet.

The first audit run "failed" on exactly this, and the defect was in the
audit's regex. That is the second time today a criterion written against one
element type was applied to another (FX3's `scrollWidth <= clientWidth` on an
`<input>`). **Grooming lesson: a criterion should name its assertion *and*
the thing it assumes about what it is asserting over.**

## Spec gaps the implementation had to close

- **Tempo on `measures[0]`.** §Rules wants `<tempo>` plus
  `scoreDef@midi.bpm` for the first measure; refinement 8 forbids
  `measures[0].tempo`. Resolved by rendering `doc.tempo` as measure 0's
  visible mark with the derived id `${measures[0].id}-tempo` — otherwise a
  generated exercise renders with no tempo marking at all.
- **`<scoreDef>` vs `<staffDef>` placement.** The doc puts `keysig`/`meter.*`
  on `<scoreDef>`; every probe puts them on `<staffDef>`. The doc was
  followed *and then measured* — key signature, meter and sounding pitch all
  render correctly. Mid-score changes emit both.
- **`spellMidi`.** "Nearest diatonic letter below, raised by one… never a
  double accidental" is self-contradictory in keys with ≥5 accidentals (D♮ in
  C♯ major would need C♯♯). Falls back to the chromatic table,
  property-tested over all 88 keys × 15 signatures.

## Criterion 9, and a red `main` it exposed

The probe suite was re-run in the orchestrating session as well. The
`verovio 4.5.1-deb523f` line is unchanged, and every residual diff traces to
Verovio-minted ids or `*Ms` timings — including `exp07`'s
`{"basic":2344→2342}`, which was checked rather than assumed: `basic` is
`tk.getMEI({basic:true}).length`, a character count, so a two-character drift
is the knock-on of minted ids having different lengths. `results.txt` was
restored and is unmodified.

Checking CI for this ticket also surfaced that **`main` was red** — pipeline
#77, the push build for FX3's merge commit, had failed in the `docker`
workflow. Not FX3's fault and not a code regression; see FX7. It is exactly
the failure `.tickets/loop.md` warns about ("a green *PR* pipeline says
nothing about whether the *push* pipeline ships"), and it was found only
because the next ticket's CI listing happened to show the previous commit's
push build. **The loop should check main's push build after every merge, not
only before starting a ticket.**

## Friction log

- vitest swallows `console.log` under this repo's config, so exploratory
  Verovio probing had to write to a file to be readable. Worth knowing for
  SC2 and every later score ticket.
- Verovio tests need the `node` environment; the per-file
  `// @vitest-environment node` docblock is the right lever, because the
  global config is `jsdom` and flipping it would move all 342 pre-existing
  tests.
