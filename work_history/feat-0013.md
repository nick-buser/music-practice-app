## The judgment, and why it is written down

Every one of these is defensible either way. That is precisely why the
choice is argued in `cadence.ts`'s doc comment rather than made silently —
a reader six months from now needs to know it was a decision, not an
accident.

| case | result | reasoning |
|---|---|---|
| no cadence set | `none` | — |
| cadence set, **never recorded** | `due` | no elapsed time exists to measure against the 2× threshold, so `overdue` has no basis; but an active cadence is not `none` either |
| **exactly at** the interval | `due` | `>=`, not `>` — the interval names the day the take is due, not the day after |
| past 2× interval | `overdue` | same `>=` reasoning |
| unparseable timestamp | `due` | treated as "never recorded" rather than silently falling through to `none` |

Both boundaries are tested **at the exact millisecond and one millisecond
short**, not at a comfortably-past value that would pass whichever way the
comparison went. Arithmetic runs on raw millisecond differences and never
on local calendar parts, so a DST crossing cannot flip a boundary — pinned
by a spring-forward test on 2026-03-15.

**"Off" is `interval_days = NULL`, and only that.** `0` is rejected by both
the Pydantic `Field(ge=1)` and a DB `CheckConstraint`, so there is exactly
one representation of "off" and no DELETE route to keep consistent with it.
Toggling off and on never accumulates rows — the unique key does that work,
pinned by `test_repeated_off_does_not_accumulate_rows`.
