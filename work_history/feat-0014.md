## The design decision

**`resolveSubject` stays synchronous, and untouched.** Bundled pieces and
scales resolve from static data; an idea cannot, because it lives behind
the API. The tempting move — making `resolveSubject` async, or letting it
fetch — would drag a network call into a pure function that the **public
static build also uses**, which is exactly the coupling `config.test.ts`
exists to forbid. Instead `subjectFromIdea` is pure and the caller supplies
the idea it already holds.

That is the whole ticket, really: keeping the pure/impure split clean while
adding a subject kind that is inherently impure to obtain.

## Verified rather than assumed

The grooming doc said SessionView rendering without a score was "already
tolerated — verify". It genuinely was — `{subject.abc ? <SessionScore/> :
"no score data"}` was pre-existing — **but it was dead code until this
ticket**, because every bundled subject has `abc` defined. Every other
`subject.*` field SessionView reads (`sections`, `hasPieceDetail`,
`byline`, `meter`, `bpmTarget`/`bpmCurrent`) was traced against an
idea-shaped Subject and none assume a piece or scale, so no render changes
were needed. `App.test.tsx` now exercises that branch live for the first
time.

Worth noting because "already tolerated" in a grooming doc is a claim, not
a fact: it happened to be true here, and the check cost one read.

## How the intent travels

`IdeaPage` → `SketchbookLive` → `SketchbookView` → `App.startSession`, via
one `onStartSession?: (id: string) => void` prop — the same callback
signature `LibraryView`, `PieceView` and `DrillsView` already use, newly
wired onto the Sketchbook branch.

Optional at every hop, deliberately: the existing `IdeaPage.test.tsx`,
`SketchbookLive.test.tsx` and `SketchbookView.test.tsx` all render these
components without the prop and keep passing untouched, and the public
build's `SketchbookMock` never receives it at all.
