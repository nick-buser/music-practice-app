## Two finds

**1. The OPS2 insert-ordering trap applies here directly — and is now
actually testable.** The completed-run path inserts a run and its property
children in one transaction: the exact shape with no guaranteed order,
because there is no `relationship()` anywhere in `app/models/` and
SQLAlchemy's unit of work sorts on ORM relationships rather than column FKs.
`get_or_create_completed_run` flushes the run before constructing a single
property, with a comment naming OPS2 as the provenance so it does not get
"simplified" later. Because the default SQLite suite structurally cannot
catch a regression here, an `@pytest.mark.integration` test exercises the
path against real Postgres — and CI's `test-postgres` step went from
**2 passed to 3 passed**, confirming it genuinely ran. That is the OPS2 →
PV1 chain closing: the CI substrate built two tickets earlier is the only
thing that can see this failure mode.

**2. `to_camel` mangles digit→letter boundaries.** `CamelModel`'s alias
generator renders `input_sha256s` as **`inputSha256S`**, not `inputSha256s`
(verified directly: `to_camel('input_sha256s') == 'inputSha256S'`). Left
alone, the API would have silently discarded every client-supplied input
hash and defaulted to `[]` — which feeds the params hash, which *is* run
identity, so it would have surfaced much later as runs mysteriously failing
to dedupe. Pinned with an explicit `Field(alias="inputSha256s")`.
**Carry forward:** any future wire field with digits followed by letters in
one segment needs the same explicit alias. The docs' contracts are full of
`sha256`/`mp3`/`utf8`-shaped names, so this will recur.

## Deliberate deviations from the groomed text

- `latest_properties` takes a `user_id`; the grooming shorthand omitted it.
  Every other read in this codebase is owner-scoped — `OwnedMixin`'s stated
  purpose.
- `executor`/`status` are `String` + `CheckConstraint`, not SQLAlchemy
  `Enum`. Nothing else in `app/models/` uses `Enum`, and a native Postgres
  enum would need a `DROP TYPE` in the downgrade that a CHECK constraint
  does not — which now matters, because CI round-trips migrations.
- The `idea_assets.run_id` FK is **not** added: SB2 has not landed, so
  `idea_assets` does not exist. Per the grooming doc, whichever lands second
  owns it — that is now SB2's job.

## Follow-up found, not fixed

`migrations/versions/0001_initial.py` uses `postgresql.JSONB()` directly for
`saved_chords.identity`, which cannot compile under the SQLite dialect
(`CompileError`). Pre-existing — reproduced on a clean pre-PV1 checkout.
Harmless in practice (Alembic only ever runs against Postgres; dev/test use
`Base.metadata.create_all`), but it means `alembic upgrade head` can never be
run against SQLite, which cost real time when trying to sanity-check `0002`
locally. `0002_provenance` deliberately uses
`sa.JSON().with_variant(postgresql.JSONB(), "postgresql")` so it does not
repeat the bug. Worth a one-line follow-up ticket to fix `0001` the same way.
