- **What landed:** three CSS properties on `.idea-title-input`. That is the
  entire diff.
- **Gates:** typecheck 0, vitest 342 passed across 35 files, build 0.
- **Routing:** T0 → haiku. One dispatch; the orchestrator then *removed*
  half of what came back, on measurement.
- **Both criteria closed**, the first on the `local (e2e)` substrate.

## The useful part: a hypothesis that measurement killed

I handed the implementer a diagnosis along with the ticket: the headline
`<input>` sits in a `flex: 1` wrapper, a flex item's default
`min-width: auto` refuses to shrink below its content's intrinsic width, an
`<input>`'s intrinsic width comes from its default `size` (~20 chars), so
the item is forced wider than the card — which matched the reported symptom
"runs past the right edge of its card". It came back implemented: a
`min-width: 0` rule plus a JSX `className` to hang it on, with a comment
stating that cause.

Then I measured it in Chrome at five viewport widths, toggling that one
property:

```
vw 1440 | min-width:0 -> input 394 right 731 contained | auto -> 394/731 contained | NO DIFFERENCE
vw 1280 | min-width:0 -> input 234 right 571 contained | auto -> 234/571 contained | NO DIFFERENCE
vw 1100 | min-width:0 -> input  54 right 391 contained | auto ->  54/391 contained | NO DIFFERENCE
vw  900 | min-width:0 -> input  43 right 380 contained | auto ->  43/380 contained | NO DIFFERENCE
vw  760 | min-width:0 -> input  43 right 380 contained | auto ->  43/380 contained | NO DIFFERENCE
```

The input was **already** inside its card at every width — `width: 100%`
inside the flex child constrains it regardless. The rule and its class were
removed before the PR.

Two things worth keeping from that:

1. **A plausible CSS cause is still a guess until it is toggled.** The
   hypothesis was specific, mechanically sound, and matched the reported
   symptom. It was also wrong. The only thing that separated the two was
   flipping the property with everything else held constant.
2. **Dead CSS carrying a false explanation is worse than no CSS.** The
   comment would have taught the next reader a mechanism that does not
   operate here. The comment now in the file states the measurement,
   including the negative result, so nobody re-adds the rule.

## What was actually wrong, and what "wrapping" could not be

The real bug was `text-overflow: clip` — a long or fallback headline was cut
mid-glyph. The fix is `overflow: hidden` + `text-overflow: ellipsis` +
`white-space: nowrap`.

The grooming doc's first suggestion — "wrap to a second line; wrapping is
likelier right for a sketchbook" — is not reachable: the headline is an
`<input>`, a single-line control, and wrapping would mean changing it to a
`<textarea>` or contenteditable. That is a behaviour change on an editable
title field, not a CSS rule, and well outside a T0 ticket. Recorded because
the doc's preference was reasonable and the constraint is invisible until
you look at the markup.

## A caveat on the acceptance criterion itself

The criterion says "assert the headline element's `scrollWidth <=
clientWidth`". That holds for the `(untitled capture)` fallback — 234 <= 234,
which is the case FX3 actually reported — but it **cannot** hold for an
arbitrary long typed value, because an `<input>`'s `scrollWidth` reports the
full text width no matter what `text-overflow` does. For typed titles the
ellipsis *is* the containment.

Not a defect in the fix, and not a reason to fail the ticket; but a criterion
written against a text element and applied to an input. Worth remembering
when grooming CSS criteria: name the assertion *and* the element it assumes.

## Two adjacent bugs found while verifying — filed, not fixed

Verification put a real browser in front of the page, which surfaced two
overflows that are **not** this ticket:

- **FX5** — a long idea title makes the Topbar breadcrumb overflow the
  viewport (`.crumb`/`.here` right=1325, topbar `.right` right=1498 at
  1280px), giving the page a horizontal scrollbar. **This is the page-level
  overflow that is easy to mistake for FX3**, and I did briefly mis-attribute
  it before probing for which element actually crossed the viewport edge.
- **FX6** — `.tech-rail` on the sketchbook stream overflows by ~18px at
  1280px, independent of any title.

Both filed in the grooming doc. Fixing either inside a T0 headline ticket
would have been scope creep, and FX5 in particular deserves its own
measurement rather than inheriting this ticket's now-disproven hypothesis.

## Verification method

`playwright-core` resolved against `app/package.json`, driving the installed
Google Chrome via `channel: 'chrome'` — zero browser downloads, per the
laptop's disk rule. A local backend on SQLite with two seeded ideas (one
untitled, one long-titled), the Vite dev server pointed at it, and a
scratchpad script measuring `scrollWidth`/`clientWidth`, the input's right
edge against the card's content box, and the document's scroll width. The
before/after was taken by stashing the fix and re-running the same script.

Cheap, repeatable, and the only reason this ticket did not land a dead rule.
