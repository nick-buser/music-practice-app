# fix-0007 — FX4: the Alembic chain runs on SQLite

- **PR:** #23 on Gitea, merged 2026-09-03 (`4d49925`). CI confirmed green
  (#52 push, #53 pull_request) before merging.
- **What:** one column in `migrations/versions/0001_initial.py` —
  `saved_chords.identity` — from a bare `postgresql.JSONB()` to an
  `IdentityJSON = sa.JSON().with_variant(postgresql.JSONB(), "postgresql")`
  alias, matching `ProvenanceJSON`/`IdeaJSON` in the later revisions. Plus
  a docstring paragraph justifying the edit, and a note in `loop.md`'s
  Alembic constraint.
- **Gates:** ruff check 0, ruff format --check 0, pyright 0, pytest 106
  passed. `openapi.json` and `schema.d.ts` untouched — no API surface.
- **Routing:** T1 → sonnet. One dispatch, no retry.

## The finding, and how long it had been sitting there

`alembic upgrade head` died on the **first** revision under SQLite:

```
CompileError: (in table 'saved_chords', column 'identity'):
  can't render element of type JSONB
```

Because this laptop has no Postgres and no Docker by policy, that one line
meant **no migration in this repo had ever been verified locally**. Every
schema ticket substituted something weaker; RC1, an hour earlier, had to
drive `0005` alone through alembic's `Operations` API and say so in its PR.

The remarkable part is that the diagnosis already existed in the codebase.
`0002_provenance.py`'s module docstring names this exact column and says
later revisions adopted `with_variant` *because* the bare type "only
compiles under the postgresql dialect and breaks `alembic upgrade head`
against SQLite". `app/models/chord.py:17` had always declared the column
the portable way. So the model was right, the convention was documented,
every subsequent revision followed it — and `0001` was simply never
revisited. It was the sole bare `postgresql.` type in the whole chain.

A known-and-unfixed bug is cheaper to find than a new one, and more
embarrassing to leave: the note in `0002` was written by someone who hit
this, worked around it, and moved on.

## Verified, not reported

Re-run in the orchestrating session against a file-backed SQLite database,
exit codes read directly rather than through a pipe:

| command | exit |
|---|---|
| `alembic upgrade head` | 0 |
| `alembic downgrade base` | 0 |
| `alembic upgrade head` | 0 |

Tables afterwards: `alembic_version, extracted_properties, extraction_runs,
idea_assets, idea_links, ideas, practice_sessions, recording_tracks,
recordings, saved_chords, users` — all eleven, including RC1's two. A
migration that errors and a migration that silently creates nothing look
alike from an exit code alone, so the table list is the part that matters.

## Why editing an applied migration was safe

On PostgreSQL `with_variant` renders `JSONB` exactly as the bare type did,
so deployed databases are unaffected and the revision id does not move —
only local runnability changes. The revision's docstring says this in
place, because the next reader would otherwise reasonably assume editing
applied history was a mistake. CI's real-Postgres round-trip
(`tests/test_integration_postgres.py`) passing on #52/#53 is the evidence
that the no-op claim holds.

## What it buys

`loop.md`'s Alembic constraint now says the chain runs locally end to end,
so the next migration ticket verifies its own round-trip instead of
substituting something weaker. RC3 and every later schema ticket get a real
`unit` substrate where they would have had a `ci`-only one.
