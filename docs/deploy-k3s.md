# Soundings on k3s

How the homelab deployment works, what it took to get green, and what to do
when it breaks. Companion to `DEPLOYMENT.md`, which covers the public
Cloudflare Pages showcase — the two never touch.

Landed 2026-08-29. Tickets: `_grooming-k3s-onboarding.md` T1–T4 here,
`service-0373` / `fix-0375` / `service-0376` in `homelab-gitops`.

## What is deployed

Two slots, one chart, both fully backed by **shared NAS services**. The chart
deploys no infrastructure: no StatefulSet, no PVC, no in-cluster Postgres or
MinIO. Postgres and Garage live on the NAS and are reached over the network.

| | prod slot | dev slot |
|---|---|---|
| URL | `https://soundings.k8s.bittern-chameleon.dev` (LAN: `soundings.k8s.lab`) | `https://soundings-dev.k8s.bittern-chameleon.dev` (LAN: `soundings-dev.k8s.lab`) |
| Argo Application | `soundings` | `soundings-dev` |
| Namespace | `soundings` | `soundings-dev` |
| Values file | `charts/soundings/values.yaml` | `charts/soundings/values-dev.yaml` |
| Database | `soundings_prod` | `soundings_dev` |
| Garage bucket | `soundings-prod` | `soundings-dev` |

Both slots track the **same image tags**. `.woodpecker/docker.yml` only builds
on pushes to `main`, so there are no dev-only images; the dev slot is a second
*data* slot on its own host, not a second image stream. A real preview slot
would need PR builds tagged `dev-<sha8>` plus a narrower `allow-tags` regexp.

## Shape

```
soundings-web (nginx :80)          soundings-api (gunicorn/uvicorn :8000)
  built with VITE_API_BASE_URL=/api    FastAPI, routers mounted at /v1
        ▲                                     ▲
        │ path /                              │ path /api  ── StripPrefix ──▶ /v1
        └──────────── Traefik Ingress ────────┘
                            ▲
                    Caddy (terminates TLS)
```

Two Ingress objects, not one with two paths: the Traefik middleware annotation
applies to *every* router an Ingress creates, and the SPA route must not be
stripped. `charts/soundings/templates/middleware.yaml` is the first Traefik
`Middleware` CRD in `homelab-gitops`.

The SPA calls `/api/v1/...` on its own origin; StripPrefix removes `/api` so
FastAPI sees `/v1/...`. This keeps the web image hostname-agnostic — the
alternative was baking the absolute public origin into the Vite build, which
would make the image environment-specific.

## Environment

Non-secret values live in each slot's `values.yaml` under `config:` and are
rendered to plain env. Secrets come from the `soundings-app` Secret in each
namespace, delivered by SOPS.

| Var | Source | Note |
|---|---|---|
| `ENV` | values | Always `prod`, in **both** slots. It is the schema-ownership switch — it stops the FastAPI lifespan calling `Base.metadata.create_all` — not the slot name. |
| `RUN_MIGRATIONS` | values | `0`. The migrate Job owns schema in-cluster; the entrypoint would otherwise run Alembic in every api pod. |
| `S3_ENDPOINT` / `S3_REGION` / `S3_BUCKET` / `S3_FORCE_PATH_STYLE` | values | Garage on the NAS. **The backend has no S3 code yet** — wired ahead of the recordings/media work so landing it needs no chart change. |
| `DATABASE_URL` | SOPS secret | DML-only `app` role. |
| `DATABASE_URL_RW` | SOPS secret | Owner/migrator. Injected into the migrate Job **only**, never the runtime pod. |
| `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | SOPS secret | Per-slot scoped Garage key. |

DSNs use the `postgresql+psycopg://` scheme — the backend pins psycopg 3, and
SQLAlchemy 2.0 would otherwise reach for psycopg2, which is not installed.
Passwords are 64 chars of `[A-Za-z0-9_-]`, so they are carried raw with no
percent-encoding.

Secrets are generated by reading Ansible Vault and piping plaintext straight
into the in-cluster `cmp-sops` sidecar. No plaintext touches the laptop, and
no local `sops` install is needed.

## The deploy loop

```
push to main → Woodpecker docker.yml → sha8 images in the Gitea registry
            → Argo CD Image Updater commits the tag to homelab-gitops
            → Argo auto-sync → rolled
```

Verified end to end on 2026-08-29 with commit `62159b38`: pushed, built,
Image Updater wrote the tag into **both** value files on `homelab-gitops`
main, Argo rolled it. No human step.

## Rough edges hit

**1. `docker.yml` could not be triggered at all.** Its single `when:` block
combined `event`/`branch` with a `path.include` filter. Path filters need a
diff to match; a manual trigger has none, so every workflow was filtered out
and Woodpecker returned `pipeline definition not found`. Both the
create-pipeline API (204, nothing created) and `wp restart` refused to produce
a build. Fixed in `fix-0002`: two OR'd conditions, with a bare `event: manual`
rule carrying no path filter.

**2. The whole deploy wedged behind an Ingress.** Traefik here never populates
`.status.loadBalancer.ingress` — every Ingress in every namespace shows
`ADDR <none>` — so Argo's Ingress health check never leaves `Progressing`.
That is why *every* tenant on this cluster reads `Synced Progressing`, and it
is harmless while an Ingress is in the last wave. It is fatal the moment
anything is gated behind one: the chart had Services + Ingresses at wave 0 and
the Deployments at wave 1, both migrate Jobs ran, and **no api or web pod was
ever created**. Fixed in `fix-0375` by inverting it — the migrate Job moved to
wave `-1` as the only resource in its wave, everything else at wave 0.

> **Rule: an Ingress may only ever be in the LAST wave.** Order by pulling
> things earlier, never by pushing things later. Now enforced by
> `scripts/chart-check.sh` in `homelab-gitops` (`service-0376`).

**3. The api container could not start: `exec: /app/docker-entrypoint.sh:
permission denied`.** The file was mode `100644` in git, so it landed
non-executable in the image. It survived every prior check because nothing had
ever run the api container — the chart's migrate Job sets `command:`, which
overrides the ENTRYPOINT outright, so Alembic ran fine against both databases
through an image whose entrypoint was broken. There is no container runtime on
this laptop by design, so no local check could have caught it either. Fixed
both ways: git mode `100755`, plus `RUN chmod +x` in the Dockerfile so a lost
mode bit cannot do this again.

**4. The gate host is unreachable.** `mlserve`, named in `homelab-gitops`'s
`.tickets/loop.md` §Gates, refuses this laptop's SSH key and has no
`~/.ssh/config` entry. Gates ran on `dev-workshop`, which needed `kyverno`
1.19.0 and `yq-go` v4.53.6 installed to become viable.

**5. `chart-check.sh` reported green on charts it had not checked.** Two
independent silent failures, both fixed in `service-0376`: with no `kyverno`
on PATH the policy loop reported nothing and printed `kyverno: clean`; and
with kislyuk's python-`yq` instead of mikefarah's Go `yq`, `blocking_policies`
emitted nothing and **every Enforce policy failure was reclassified as an
Audit-only advisory**.

## Operating it

```bash
# state
ssh dev-workshop kubectl -n argocd get app soundings soundings-dev
ssh dev-workshop kubectl get pods -n soundings
ssh dev-workshop kubectl -n soundings logs deploy/soundings-api --tail=40

# both apps read "Synced Progressing" forever — see rough edge 2. Health is
# only meaningful as Degraded (a real problem) vs Progressing (normal here).
```

**Sync stuck** on `waiting for healthy state of ...`:

```bash
ssh dev-workshop kubectl -n argocd patch app soundings --type json \
  -p '[{"op":"remove","path":"/operation"}]'
ssh dev-workshop kubectl -n argocd annotate application soundings \
  argocd.argoproj.io/refresh=hard --overwrite
```

**Roll back:** revert the Image Updater tag commit on `homelab-gitops` main.
Argo picks it up within its 3-minute poll.

**New Application not appearing after a merge:** refresh the app-of-apps —
`kubectl -n argocd annotate application apps argocd.argoproj.io/refresh=normal --overwrite`.

## Known open

- `.woodpecker/backend.yml`'s `typecheck` step fails on main with exit 127:
  `pyright` downloads its own nodeenv and that node cannot load
  `libatomic.so.1` in the CI step image. Pre-existing and unrelated to the
  deploy — it only surfaced now because earlier pipelines never matched
  `backend.yml`'s path filter. The image builds are a separate workflow and
  are unaffected.
- The backend has no S3 code, so the Garage credentials are delivered but
  unused.
- No preview slot (see "What is deployed").
