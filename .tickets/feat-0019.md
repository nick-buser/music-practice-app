## Description

Unplanned, operator-driven: Nick has a folder of quick captures off Keyscape
(`~/Documents/piano_snippets`) — three takes, each bounced to `.mid`, `.wav`
and a `.keyscape` patch — and nothing had ever been imported into the
sketchbook. The prod slot's `ideas` table was empty. Getting real material in
is the point; the script is the vehicle, not the goal.

**Tier:** T2 (new operator tool; sets the pattern the REAPER ideas-inbox
sidecar will follow)
**Depends on:** SB1 (ideas), SB2 (idea assets), MD1 (Garage) — all merged

**Why:** The sketchbook has had a full capture spine since SB1–SB7 and zero
real content in it. A one-off `curl` would have put the bytes in and taught
nobody anything; snippets arrive in batches on a repeating filename
convention, so the import wants to be a re-runnable tool.

**Scope / surfaces / files:**
- `backend/scripts/import_snippets.py`: group a directory by filename stem
  (one stem = one idea, in however many formats), derive title / key /
  `capturedAt` from the `YYYY-MM-DD_<key>_<name>` convention, and upload each
  file through `POST /v1/ideas/{id}/assets` with the role
  `docs/sketchbook.md` assigns it. Stdlib only (`urllib`) — an import must
  never be the reason a dependency gets installed.
- Roles follow the doc's "raw is immortal, derived is recomputable" split:
  `.mid` → `melody` (the played-in take *is* the idea), the bounce →
  `render`, the Spectrasonics patch → `other` (it is none of the musical
  roles, and `rpp` is named for REAPER projects).
- Idempotent by construction: idea id is `uuid5(_NAMESPACE, stem)`, so a
  re-run recognises its own rows instead of duplicating them; an asset whose
  sha256 the idea already carries is skipped.
- `backend/tests/test_import_snippets.py`: the conventions, the roles, and
  the pinned ids.
- `backend/pyproject.toml`: `scripts` joins `app` as ruff first-party.

**Deliberately not in scope:** deriving tempo, note count, duration or a key
*guess* from the notes. That is `midi-features`
(`app/jobs/extractors/midi_features.py`), which the `.mid` upload enqueues on
its own. The importer only reads what the capture already stated.

## Notes

**Two bugs found while building it, both worth recording.**

1. **The key regex matched nothing it was written for.** It used `\b`
   boundaries around the tonic and mode — but every filename in the
   convention separates words with `_`, and `_` is a word character, so
   `\b` matches *nowhere* in `2026-09-06_a_minor_melody1`. `parse_key`
   silently returned `None` for all three real snippets, and the dry run
   still *looked* right because the title's leading capital came from the
   final `.upper()`, not from the key substitution. Fixed with explicit
   `(?<![a-z])` / `(?![a-z])` lookarounds; the three real stems are now
   parametrised test cases so it cannot regress into silence again.

2. **The backend venv's console scripts had dead shebangs.** The repo moved
   into `personal_coding/music/` on 2026-09-08, and `.venv/bin/*` still
   pointed at `personal_coding/music-practice-app/backend/.venv/bin/python`.
   So `uv run pytest` — the exact command `.tickets/loop.md` names as a gate
   — failed with `ModuleNotFoundError: No module named 'fastapi'`, while
   `uv run python -m pytest` passed. 34 scripts repaired in place (no
   reinstall, no download). Anything driving the documented gates from a
   fresh session on this laptop would have hit this.

**The worker is embedded in the api process, and it works.** An early read of
`kubectl -n soundings get deploy` (only `soundings-api` and `soundings-web`)
led to the wrong conclusion that nothing executes queued runs. It does:
`app/main.py`'s lifespan starts `run_forever` on a daemon thread when
`settings.worker_embedded` is true, which is the default (PV2 — a separate
worker Deployment was deliberately deferred while exactly one api replica
runs). All three `midi-features` runs enqueued by this import reached
`succeeded` within seconds.

**The extracted facts corroborate an independent parse.** Note counts
(121 / 259 / 69), pitch ranges (64-84, 60-76, 40-81) and durations
(79.9 s / 82.7 s / 51.6 s) match a from-scratch SMF parse of the same three
files exactly.

**One thing for Nick, not a bug.** `key_guess` for #3 *A minor somber* is
**C major** (confidence 0.77) while the filename says A minor — and the
importer stored `key: "A minor"` from the name. Both are defensible: that
take uses the natural-minor collection with no accidentals at all, so its
pitch-class content is identical to C major and Krumhansl-Schmuckler picks
the relative major. The human-stated key wins in the `key` field; the guess
stays a separate, confidence-carrying property. Worth knowing before anyone
treats `key_guess` as ground truth for relative-key material. (#1 and #2
agree with their filenames: A minor 0.81, D minor 0.76.)

**Verified in the deployed UI, not just the API.** The prod sketchbook stream
shows "Ideas captured 3 / In the inbox 3" with all three in reverse-
chronological order; idea #1's page renders its three attachments with the
right role badges and sizes, an inline player for the 20.6 MB bounce, `key`
as `A minor`, and all six `midi-features` properties with their producer
attribution. No console errors.

**Two small things noticed there, neither in scope.** The sidebar's Sketchbook
count is still the hardcoded `3` from the mock (it now happens to be right,
which makes it *more* misleading, not less); and `.mid` attachments get an
inline `<audio>` player that no browser can decode, so it renders as a dead
0:00 / 0:00 control next to the working one on the `.wav`.
