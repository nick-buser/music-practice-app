## Problem

`.woodpecker/backend.yml`'s `typecheck` step fails on `main` with exit 127:

```
+ cd backend
+ uv run pyright
* Install prebuilt node (26.8.1) ... done.
/root/.cache/pyright-python/nodeenv/bin/node:
  error while loading shared libraries: libatomic.so.1:
  cannot open shared object file: No such file or directory
```

`pyright-python` downloads its own prebuilt node on first run. That binary
links against `libatomic`, which `bookworm-slim` does not ship — so the
typecheck step can never have worked in CI.

**This is not homelab infra.** The step image is a public upstream one
(`ghcr.io/astral-sh/uv:python3.12-bookworm-slim`) declared in this repo's own
`.woodpecker/backend.yml`, and this is the only repo on the machine running
pyright in CI. Nothing homelab-managed is involved; the fix belongs here.

## Why it surfaced only now

`backend.yml` has a `path.include` filter on `backend/**`. Pipelines 1–8 never
touched `backend/`, so the workflow never ran. Pipeline 9 (commit `62159b38`,
the `docker-entrypoint.sh` mode fix) was the first push to match it, on
2026-08-29 — the day the k3s deploy landed.

## Options

1. `apt-get update && apt-get install -y libatomic1` at the top of the
   typecheck step. Smallest diff; costs an apt round-trip per run.
2. Set `PYRIGHT_PYTHON_FORCE_VERSION` and pre-install a node that works, or
   point pyright at a system node so it skips nodeenv entirely.
3. Use a non-slim image for the typecheck step only.
4. Drop pyright from CI and rely on the local gate in `.tickets/loop.md`.
   Cheapest, and honest about what is actually enforced — but then nothing
   type-checks the backend on a push.

Option 1 or 2. Prefer 2 if the download is what is slow; 1 if it isn't.

## Acceptance criteria

- [ ] `typecheck` goes green on a push touching `backend/**`
- [ ] the fix is exercised by that same push, not asserted — this step has no
      local gate (no container runtime on the laptop, by design)
- [ ] `pytest` (currently `skipped`, because it runs after `typecheck`) also
      runs and goes green, so the whole workflow is proven, not just the step
      that was red

## Notes

The image builds are a **separate workflow** in the same pipeline and were
unaffected — `soundings-api` and `soundings-web` both pushed `62159b38`
successfully while this step was failing. So this never blocked the k3s
deploy, and does not block it now. It does mean `main` currently carries a red
pipeline.

Context: `docs/deploy-k3s.md` §Known open.

## Implemented 2026-08-30 — option 1

`apt-get install -y --no-install-recommends libatomic1` at the top of the
typecheck step. Chosen over the nodeenv-bypass options because it is one line,
keeps the same image as every other step, and the package is tiny.

**Verified before pushing, in the exact CI image**, using Docker on
dev-workshop (there is none on the laptop, by design):

- reproduced: `uv run pyright` → the libatomic.so.1 error, same as pipeline 9
- with libatomic1 installed: `0 errors, 0 warnings, 0 informations`
- `uv run pytest -q` in the same image: **13 passed, 13 deselected** — so the
  `test` step, which has only ever been reported as `skipped`, does pass once
  it is allowed to run
