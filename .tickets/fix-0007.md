## Description

Groomed as **FX4** in `.tickets/_grooming-sketchbook-and-media.md` (found in
flight by RC1, feat-0011).

**Tier:** T1
**Depends on:** —

`uv run alembic upgrade head` fails at the **first** revision under SQLite:

```
CompileError: (in table 'saved_chords', column 'identity'):
  can't render element of type JSONB
```

`migrations/versions/0001_initial.py:45` declares
`sa.Column("identity", postgresql.JSONB(), nullable=False)`.

**This was already diagnosed and never fixed.** `0002_provenance.py`'s own
docstring says it outright:

> JSON columns use `JSON().with_variant(JSONB(), "postgresql")` … rather
> than `postgresql.JSONB()` directly (as `0001_initial.py` uses for
> `saved_chords.identity`) — the latter only compiles under the postgresql
> dialect and breaks `alembic upgrade head` against SQLite

Every revision from 0002 on adopted `with_variant` *because of this*, and
`app/models/chord.py:17` already declares the column as
`IdentityJSON = JSON().with_variant(JSONB(), "postgresql")`. So the
migration has been inconsistent with the model whose table it creates.

**Why it matters beyond one line:** this laptop has no Postgres and no
Docker by policy, so the whole chain being un-runnable means **no migration
in this repo has ever been verified locally**. Every schema ticket
substitutes something weaker (RC1 drove `0005` alone through alembic's
`Operations` API) and the authoritative check happens only in CI.

## Notes

Editing an already-applied migration is deliberate and safe here: on
Postgres `with_variant` renders `JSONB` exactly as the bare type did, so
deployed databases are unaffected and the revision id is unchanged. The
revision must say why an applied migration was edited.
