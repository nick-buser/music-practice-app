## Notes

**The mock move is verbatim, and that was verified rather than asserted.**
`app/e2e/stats-and-sketchbook.spec.ts` pins `.sketch-grid`,
`.lyric-block .marker`, `.sketch-detail .tabs button`, `.chord-row .chord`
(exactly 5) and `.harmony-score svg g.note` — and Playwright browsers are
deliberately absent on this laptop, so no gate available here can catch a
break in that markup. Checked directly in the orchestrating session:
`diff <(git show HEAD:app/src/views/SketchbookView.tsx) app/src/views/SketchbookMock.tsx`
reports **one** changed line, the export rename. `git diff` on
`app/src/styles/app.css` is empty — zero new CSS, existing classes reused.

**Sidebar count threading.** `NAV` in `Sidebar.tsx` is a module-level const,
so it cannot read live state. `Sidebar` gained an optional
`counts?: Partial<Record<View, number>>` override that falls back to each
item's static count, leaving the `.count`/`.active` markup untouched.
`App.tsx` computes the live value.

**Known trade-off, accepted for this ticket:** `App.tsx` runs its own
`useIdeas(true)` for the badge, independent of the instance `SketchbookLive`
owns for the stream. That means two `GET /v1/ideas` calls while the
Sketchbook tab is open, and no shared cache — so a capture updates the stream
immediately but the badge only catches up on its next fetch or a reload. The
acceptance criterion checks the count after a reload, so this satisfies it;
if the lag ever reads as a bug, the fix is lifting the hook to a shared
context, which is a bigger change than SB3a should carry.

**Contract bug found and filed, not fixed:** the SB2 streaming download route
is documented in `openapi.json` as returning `application/json` with an empty
schema, though it returns real binary at runtime (the SB2 deploy check
round-tripped 1 MB with a correct `Content-Type` and `ETag`). Every generated
client therefore types it as JSON `unknown`, which is why no typed
`downloadIdeaAsset` exists yet. Filed as **FX1** in the grooming doc.
