## Notes

Merged as PR #27 (`2041fc8`); CI green (#66, #67). Full account in
`work_history/feat-0015.md`. 128 backend tests (was 113), 299 frontend

Substrate probe for this run (2026-09-03): unit UP (113 backend tests green
on `3d22bd6`), ci UP (push pipeline #63 success on `3b6c7d0`), deployed UP
(`/api/healthz` → `{"status":"ok","storage":"ok"}`).

**Deviation from the groomed scope:** the doc said "model declares the
column with a SQLite no-op variant". `search_tsv` is instead an *unmapped*
`column("search_tsv", TSVECTOR)` expression — SQLAlchemy 2.0 has no
per-dialect `Computed()`, so mapping it would force `create_all()` to emit
either an expression SQLite cannot execute or a never-populated tsvector on
Postgres. Consequence: the integration test runs the real migrations rather
than `create_all()`, which is the stronger test anyway.

**CI earned its keep here.** Eight local gates were green while the
`-m integration` test was broken: it copied the `s.add(User(...))` idiom
from its `create_all()`-based neighbours, but `0001_initial` seeds the
default user, so running the real migrations duplicated `users_pkey`
(pipeline #64). Fixed with the idempotent `ensure_default_user`. The same
run also confirmed the thing this laptop cannot check — that the `STORED`
generated column's `to_tsvector`/`tags::text` expression is accepted as
IMMUTABLE.

**Deployed check (criterion 4)** ran `?q=hello` → total 1, handle [1], plus
`?q=zzznomatch` → total 0 as a control, so the pass is a filter working and
not a coincidence.

**Follow-up worth a ticket, not fixed here (out of scope):** the SQLite
free-text branch interpolates into `LIKE '%…%'` without escaping `%`/`_`,
so those characters act as wildcards. Postgres path unaffected.
